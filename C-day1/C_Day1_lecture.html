개발환경과 첫 컴파일

09:00–09:50

학습 목표

  • hello.c 를 컴파일하고 실행한다
  • 컴파일과 실행이 다른 일임을 설명한다
  • main 의 반환값이 어디로 가는지 확인한다

▶ 예제 1-1 · hello.c

hello.c

#include <stdio.h>

int main(void) {
    printf("Hello, C!\n");
    return 0;
}

gcc hello.c            # 출력 이름을 안 주면 a.out
ls                     # a.out  hello.c
./a.out                # → Hello, C!
gcc hello.c -o hello   # 이름 지정
./hello                # → Hello, C!

Python과 다른 점: 소스를 고치면 다시 컴파일해야 실행 결과가 바뀝니다. 한 번 해 보세요 — 문자열을 바꾸고 ./hello 만 다시 실행하면 옛날 결과가 나옵니다.

▶ 예제 1-2 · main 의 반환값은 어디로 가는가

#include <stdio.h>

int main(void) {
    printf("센서 초기화 실패\n");
    return 7;                  // 0 이 아니면 "비정상 종료" 라는 약속
}

gcc -Wall -Wextra exitcode.c -o exitcode
./exitcode; echo "종료 코드: $?"     # → 종료 코드: 7

$? 는 직전 프로그램의 종료 코드입니다. 셸 스크립트·Makefile·systemd 가 이 값으로 성공/실패를 판단합니다. Jetson 에서 서비스가 죽었는지 확인할 때 다시 만납니다.

▶ 예제 1-3 · ⚠ 함정 — 헤더를 빼면

int main(void) {
    printf("Hello\n");     // stdio.h 없음
    return 0;
}

gcc -Wall -Wextra nohdr.c -o nohdr
# → error: implicit declaration of function 'printf'

헤더는 "이런 함수가 있다" 는 선언을 담습니다. 컴파일러는 선언 없이는 printf 의 인자·반환 타입을 검사할 수 없습니다. 3교시에서 선언과 정의를 정확히 나눕니다.

✏️ 괄호 넣기 1-2

  1. 출력 이름을 지정하지 않은 gcc hello.c 는 파일을 만든다.
  2. 소스를 고친 뒤 결과를 바꾸려면 반드시 다시 해야 한다.
  3. main 의 반환값은 셸에서 로 읽을 수 있고, 이 정상 종료를 뜻한다.
  4. printf 를 쓰려면 헤더를 include 해야 한다.

2교시

빌드 과정 해부

10:00–10:50

학습 목표

  • 전처리 → 컴파일 → 어셈블 → 링크 네 단계를 각각 멈춰 세워 산출물을 본다
  • "undefined reference" 가 어느 단계의 에러인지 안다

🎬 D1-1 빌드 파이프라인 — 상자를 하나씩 눌러 산출물을 확인하며 진행

▶ 예제 2-1 · 네 단계를 따로 실행

gcc -E hello.c -o hello.i     # ① 전처리:  #include, #define 을 풀어 씀
gcc -S hello.i -o hello.s     # ② 컴파일:  C → 어셈블리
gcc -c hello.s -o hello.o     # ③ 어셈블:  어셈블리 → 기계어 (오브젝트)
gcc hello.o -o hello          # ④ 링크:    오브젝트 + libc → 실행파일
ls hello*                     # hello  hello.c  hello.i  hello.o  hello.s

wc -l hello.c hello.i         # → 6 hello.c / 800줄 안팎 hello.i

6줄이 800줄이 된 이유: #include <stdio.h> 는 그 파일을 그 자리에 통째로 붙여넣기 하라는 뜻입니다. hello.i 맨 아래로 내려가 보면 우리가 쓴 main 이 그대로 있습니다.

▶ 예제 2-2 · 어셈블리 읽기 — printf 가 사라졌다?

cat hello.s

.LC0:
        .string "Hello, C!"
main:
        pushq   %rbp
        movq    %rsp, %rbp
        leaq    .LC0(%rip), %rdi
        call    puts@PLT          # ← printf 가 아니라 puts
        movl    $0, %eax
        popq    %rbp
        ret

서식(%d 등)이 없고 \n 으로 끝나는 printf 는 컴파일러가 더 단순한 puts 로 바꿉니다. 컴파일러가 코드를 "그대로" 번역하지 않는다는 첫 번째 증거입니다.

▶ 예제 2-3 · 오브젝트는 아직 puts 의 주소를 모른다

nm hello.o
#                  U puts     ← U = undefined. "누군가 채워 줘야 함"
# 0000000000000000 T main     ← T = text(코드). 여기서 정의됨

nm hello | grep -E "main|puts"
# 0000000000001139 T main
#                  U puts@GLIBC_2.2.5   ← 링크 후: 실행 시 libc.so 에서 찾기로 연결됨

🎬 D1-1 링커 단계에서 옆에서 합쳐지는 libc 상자가 이것입니다.

▶ 예제 2-4 · ⚠ 함정 — 링크 에러 만들어 보기

link_err.c

#include <stdio.h>
int read_sensor(void);          // 선언만 있고 정의(본문)가 없다

int main(void) {
    printf("%d\n", read_sensor());
    return 0;
}

gcc -c link_err.c               # ③ 어셈블까지는 성공! (선언이 있으니 컴파일러는 만족)
gcc link_err.o -o link_err      # ④ 링크에서 실패
# → undefined reference to `read_sensor'

"컴파일은 됐는데 undefined reference" 는 정의를 어느 .o 에서도 못 찾았다 는 링커의 말입니다. 함수 이름 오타, .c 파일 빠뜨림, 라이브러리 옵션(-lm) 누락이 단골 원인입니다.

▶ 예제 2-5 · 최적화 수준 비교

gcc -S -O0 hello.c -o o0.s
gcc -S -O2 hello.c -o o2.s
wc -l o0.s o2.s               # -O2 가 더 짧다
diff o0.s o2.s                # pushq %rbp / movq %rsp,%rbp 가 사라진 것을 확인

-O0 는 디버깅하기 쉽게 코드를 그대로, -O2 는 프레임 포인터 생략 등으로 줄입니다. 임베디드 릴리스 빌드는 -O2 또는 크기 우선 -Os.

✏️ 빈칸 채우기 2-1

각 단계에서 멈추는 옵션을 채우세요.

gcc  hello.c -o hello.i     # 전처리까지
gcc  hello.i -o hello.s     # 어셈블리까지
gcc  hello.s -o hello.o     # 오브젝트까지
gcc hello.o -o hello            # 링크
🔒 정답 보기 2-1 
gcc -E hello.c -o hello.i
gcc -S hello.i -o hello.s
gcc -c hello.s -o hello.o

✏️ 괄호 넣기 2-2

  1. #include 를 풀어 쓰는 단계는 이고, 그 결과 파일 확장자는 이다.
  2. nm hello.o 의 U puts 는 puts 가 상태라는 뜻이며, 단계에서 해결된다.
  3. "undefined reference to X" 는 X 의 을(를) 못 찾았다는 뜻이다.
  4. 서식 없는 printf("...\n") 를 컴파일러가 로 바꾸는 것은 최적화의 예다.
🔒 정답 보기 2-2 1. 전처리 / `.i` 2. 미해결(undefined) / 링크 3. 정의 4. puts

헤더/소스 분리와 Makefile

11:00–11:50

학습 목표

  • 선언은 .h 에, 정의는 .c 에 나누고 헤더 가드를 붙인다
  • Makefile 로 다중 파일 프로젝트를 빌드하고, 바뀐 파일만 다시 컴파일되는 것을 본다

🎬 D1-2 헤더 가드 — 토글을 끄고 재정의 에러부터 본다

▶ 예제 3-1 · 파일 3개로 나누기

sensor.h — 선언 (무엇이 있는지)

#ifndef SENSOR_H
#define SENSOR_H

typedef struct {
    double t;      // 온도
    int    h;      // 습도
    int    d;      // 거리(mm)
} Reading;

int  is_alert(Reading r);
void print_reading(Reading r);

#endif

sensor.c — 정의 (실제 본문)

#include <stdio.h>
#include "sensor.h"

int is_alert(Reading r) {
    return r.t > 35.0;
}

void print_reading(Reading r) {
    printf("T=%.1f H=%d D=%d %s\n", r.t, r.h, r.d, is_alert(r) ? "ALERT" : "OK");
}

main.c

#include "sensor.h"

int main(void) {
    Reading r1 = {25.3, 60, 120};
    Reading r2 = {36.9, 70, 150};
    print_reading(r1);     // → T=25.3 H=60 D=120 OK
    print_reading(r2);     // → T=36.9 H=70 D=150 ALERT
    return 0;
}

gcc -Wall -Wextra main.c sensor.c -o app && ./app

"sensor.h" (따옴표) 는 현재 폴더에서 먼저 찾고, <stdio.h> (꺾쇠) 는 시스템 경로만 찾습니다. 구조체 문법은 Day 3 에서 자세히 — 오늘은 "여러 값을 한 묶음으로" 정도로만 읽으세요.

▶ 예제 3-2 · ⚠ 함정 — 헤더 가드를 지우면

sensor.h 의 #ifndef / #define / #endif 세 줄을 지우고, main.c 에 #include "sensor.h" 를 두 번 쓰세요.

gcc -Wall -Wextra main.c sensor.c -o app
# → error: redefinition of 'struct <anonymous>'
# → error: conflicting types for 'Reading'

함수 선언은 몇 번 나와도 되지만, 구조체·typedef 정의는 한 번만 허용됩니다. a.h 와 b.h 가 같은 공용 헤더를 include 하는 순간 실제 프로젝트에서 반드시 일어나는 일입니다. 가드를 되돌리고 다시 빌드하세요.

▶ 예제 3-3 · Makefile — 바뀐 것만 다시

Makefile (명령 줄 앞은 반드시 탭)

CC     = gcc
CFLAGS = -Wall -Wextra -O2

app: main.o sensor.o
    $(CC) $(CFLAGS) -o app main.o sensor.o

main.o: main.c sensor.h
    $(CC) $(CFLAGS) -c main.c

sensor.o: sensor.c sensor.h
    $(CC) $(CFLAGS) -c sensor.c

clean:
    rm -f *.o app

make            # 세 줄의 gcc 가 실행됨
make            # → make: 'app' is up to date.   (아무것도 안 함)
touch sensor.c  # sensor.c 만 "수정"
make            # sensor.o 와 app 만 다시 만들어짐
touch sensor.h  # 헤더 수정
make            # main.o, sensor.o, app 전부 — 둘 다 sensor.h 에 의존하므로
make clean      # 산출물 삭제

타깃: 의존파일 규칙에서 의존 파일이 타깃보다 새로우면 명령을 실행합니다. 헤더를 의존성에 적지 않으면 헤더를 고쳐도 오래된 .o 가 그대로 링크되어 "분명 고쳤는데 안 바뀌는" 버그가 됩니다.

▶ 예제 3-4 · 경고 읽는 연습

main.c 에 int unused = 1; 한 줄을 넣고 make 하세요.

main.c:5:9: warning: unused variable 'unused' [-Wunused-variable]

파일:줄:열 — 경고 종류 — [옵션 이름]. 오늘 나오는 경고는 전부 실제 버그의 신호입니다. 경고 0 개가 제출 조건입니다.

✏️ 빈칸 채우기 3-1

#endif

✏️ 괄호 넣기 3-2

  1. 헤더에는 을, .c 파일에는 를 둔다.
  2. 같은 헤더가 두 번 들어와도 에러가 나지 않게 하는 것이 이다.
  3. Makefile 규칙의 명령 줄 앞에는 공백이 아니라 문자가 와야 한다.
  4. make 는 의존 파일의 를 비교해 필요한 것만 다시 만든다.
🔒 정답 보기 3-2 1. 선언 / 정의 2. 헤더 가드 (`#ifndef` … `#endif`) 3. 탭 4. 수정 시각(타임스탬프)

🎬 D1-3 메모리 바이트 뷰어 (300 을 uint8_t 로) · D1-4 2의 보수 다이얼 (127 → 128)

규칙: 예측 먼저 쓰고, 그 다음 실행합니다.

▶ 예제 4-1 · sizeof — 예측 후 확인

#include <stdio.h>
#include <stdint.h>

int main(void) {
    printf("char     %zu\n", sizeof(char));
    printf("short    %zu\n", sizeof(short));
    printf("int      %zu\n", sizeof(int));
    printf("long     %zu\n", sizeof(long));
    printf("float    %zu\n", sizeof(float));
    printf("double   %zu\n", sizeof(double));
    printf("uint8_t  %zu\n", sizeof(uint8_t));
    printf("int32_t  %zu\n", sizeof(int32_t));
    printf("int *    %zu\n", sizeof(int *));
    return 0;
}

char 1 · short 2 · int 4 · long 8 · float 4 · double 8 · uint8_t 1 · int32_t 4 · int * 8   (x86-64 Linux)

long 은 Windows 에서 4, int * 는 32비트 MCU(ESP32)에서 4 입니다. 플랫폼마다 다르기 때문에 임베디드는 stdint.h 의 고정폭 타입(uint8_t, int32_t …)을 씁니다. %zu 는 size_t 출력용 서식입니다.

▶ 예제 4-2 · 바이트로 보기 — 리틀 엔디안

#include <stdio.h>

int main(void) {
    int v = 0x11223344;
    unsigned char *p = (unsigned char *)&v;    // v 의 첫 바이트 주소 (Day 2 에서 자세히)
    printf("%02X %02X %02X %02X\n", p[0], p[1], p[2], p[3]);   // → 44 33 22 11
    return 0;
}

낮은 주소에 낮은 바이트(LSB) 가 옵니다. 메모리 덤프나 시리얼로 받은 바이트가 "거꾸로" 보이는 이유이며, 네트워크 바이트 순서(빅 엔디안)와 반대라 통신 프로토콜에서 항상 확인해야 합니다. 🎬 D1-3 엔디안 토글.

▶ 예제 4-3 · ⚠ 함정 — 넘치면 잘린다

#include <stdio.h>
#include <stdint.h>

int main(void) {
    uint8_t a = 250;
    a += 10;                    // 260 은 8비트에 없다
    int8_t b = 127;
    b++;                        // 01111111 + 1
    int x = 300;
    unsigned char c = x;        // 0x12C 에서 하위 1바이트만
    printf("%d %d %d\n", a, b, c);
    return 0;
}

예측: ______   실제: 4 -128 44

  • a: 260 − 256 = 4 (감김, wrap-around)
  • b: 최상위 비트가 1이 되어 −128. signed 오버플로는 C 표준상 정의되지 않은 동작이라 컴파일러가 뭘 해도 됩니다 — 실제 코드에서는 절대 의존하지 마세요
  • c: 300 = 0x12C → 하위 바이트 0x2C = 44

🎬 D1-3 에서 300 을 넣고 자료형을 uint8_t 로 바꿔 상위 바이트가 떨어져 나가는 것을 보세요.

▶ 예제 4-4 · 같은 비트, 다른 해석

🎬 D1-5 정수 승격 함정 — -1 < 1u 재생

▶ 예제 5-1 · ⚠ 함정 — -1 은 1 보다 작다. 정말?

#include <stdio.h>

int main(void) {
    printf("%d\n", -1 < 1);              // → 1  (참)
    printf("%d\n", -1 < 1u);             // → 0  (거짓!)
    printf("%d\n", -1 < sizeof(int));    // → 0  (거짓!)

    return 0;
}

# warning: comparison of integer expressions of different signedness [-Wsign-compare]

int 와 unsigned int 를 비교하면 int 쪽이 unsigned 로 변환됩니다. −1 의 비트 0xFFFFFFFF 는 unsigned 로 4294967295. sizeof 의 결과 타입이 size_t(unsigned) 라서 배열 길이와 음수 인덱스를 비교하는 코드가 이 함정에 자주 빠집니다. -Wextra 가 잡아 줍니다.

▶ 예제 5-2 · 정수 승격 — char 도 계산하면 int

#include <stdio.h>

int main(void) {
    char c = 'A';
    printf("%zu %zu\n", sizeof(c), sizeof(c + 1));    // → 1 4
    printf("%c %d\n", c + 1, c + 1);                  // → B 66
    return 0;
}

int 보다 작은 타입은 연산에 들어가는 순간 int 로 승격됩니다. 4교시의 uint8_t a += 10 도 사실 int 로 계산한 뒤 다시 8비트로 잘라 넣는 것입니다.

▶ 예제 5-3 · ⚠ 함정 — 정수 나눗셈

#include <stdio.h>

int main(void) {
    printf("%d\n",   7 / 2);        // → 3     (정수 나눗셈, 버림)
    printf("%.1f\n", 7 / 2.0);      // → 3.5   (한쪽만 실수여도 실수 연산)
    printf("%d\n",   7 % 2);        // → 1     (나머지)

    int c = 26;
    double f1 = c * 9 / 5 + 32;     // 왼쪽부터: 234 / 5 = 46 (이미 잘림)
    double f2 = c * 9.0 / 5 + 32;
    printf("%.1f %.1f\n", f1, f2);  // → 78.0 78.8
    return 0;
}

c = 25 로 바꾸면 둘 다 77.0 으로 우연히 맞습니다. 테스트 값 하나로 안심하면 안 되는 이유.

▶ 예제 5-4 · 실수 비교

#include <stdio.h>
#include <math.h>

int main(void) {
    double a = 0.1 + 0.2;
    printf("%d\n", a == 0.3);                  // → 0

    return 0;
}

▶ 예제 6-2 · switch — 공은 벽을 만날 때까지 굴러간다

#include <stdio.h>

    switch (level) {
        case 1:  printf("FREEZE ");
        case 2:  printf("COLD ");           // break 없음
        case 3:  printf("NORMAL "); break;
        case 4:  printf("WARM ");

    return 0;
}

case 는 블록이 아니라 점프 목적지입니다. level 을 1, 4, 9 로 바꿔 각각 무엇이 출력되는지 예측한 뒤 실행하세요. 🎬 D1-6.

case 1:
    prepare();
    // fall through      ← 의도 표시
case 2:

#include <stdio.h>

int is_prime(int n) {

    for (int i = 2; i * i <= n; i++)      // √n 까지만 검사

}

        printf("%3d ", n);

    }
    printf("\n");
    return 0;
}

🎬 D1-7 스택 프레임 — fact(3) 을 한 단계씩

▶ 예제 7-1 · 값 전달 — 복사본이 바뀔 뿐

#include <stdio.h>

    printf("안: %d\n", x);

원본을 바꾸려면 주소를 넘겨야 합니다 — Day 2 포인터의 첫 번째 동기입니다.

▶ 예제 7-2 · 재귀와 static — 스택 vs 데이터 영역

#include <stdio.h>

static int calls = 0;             // 데이터 영역: 프로그램 끝까지 산다

int fact(int n) {
    calls++;
    printf("%*sfact(%d) 진입\n", (3 - n) * 2, "", n);   // 들여쓰기로 깊이 표시
    if (n <= 1) return 1;
    int r = n * fact(n - 1);
    printf("%*sfact(%d) → %d\n", (3 - n) * 2, "", n, r);
    return r;
}

int main(void) {
    int r = fact(3);              // 먼저 변수에 받는다 — 이유는 예제 7-4 에서
    printf("결과 %d, 호출 %d번\n", r, calls);
    return 0;
}

fact(3) 진입
  fact(2) 진입
    fact(1) 진입
  fact(2) → 2
fact(3) → 6
결과 6, 호출 3번

들어갈 때는 3→2→1, 돌아올 때는 1→2→3. 가장 나중에 쌓인 프레임이 먼저 사라집니다(LIFO). calls 는 프레임과 무관하게 계속 남습니다. 🎬 D1-7 에서 프레임 push/pop 과 오른쪽 데이터 영역을 비교하세요.

▶ 예제 7-3 · 함수 안의 static — 호출 사이에 값 유지

#include <stdio.h>

int next_id(void) {
    static int id = 0;            // 첫 호출에 한 번만 초기화
    return ++id;
}

int main(void) {
    printf("%d\n", next_id());    // → 1
    printf("%d\n", next_id());    // → 2
    printf("%d\n", next_id());    // → 3
    return 0;
}

같은 static 이지만 파일 범위 함수/전역에 붙으면 뜻이 다릅니다: "이 파일 밖에서 보이지 않음" (internal linkage). 다른 .c 와 이름이 겹쳐도 충돌하지 않게 하는 용도로 Day 3·4 에서 씁니다.

▶ 예제 7-4 · ⚠ 함정 — 인자 평가 순서는 정해져 있지 않다

#include <stdio.h>

int next_id(void) { static int id = 0; return ++id; }

int main(void) {
    printf("%d %d %d\n", next_id(), next_id(), next_id());   // → 3 2 1  (gcc)
    return 0;
}

1 2 3 을 기대했겠지만 gcc 는 오른쪽 인자부터 평가합니다. C 표준은 순서를 정하지 않으므로 부수효과가 있는 호출을 한 식에 여러 번 넣지 마세요. 순서가 중요하면 변수에 먼저 받습니다.

예제 7-2 의 main 을 printf("결과 %d, 호출 %d번\n", fact(3), calls); 로 바꿔 보세요. gcc 에서는 calls 가 먼저 읽혀 "호출 0번" 이 나옵니다 — 같은 함정입니다.

▶ 예제 7-5 · 재귀의 한계

#include <stdio.h>
int depth(int n) { return n == 0 ? 0 : 1 + depth(n - 1); }
int main(void) {
    printf("%d\n", depth(10000));       // 보통 OK
    printf("%d\n", depth(10000000));    // → Segmentation fault (스택 오버플로)

이동평균 필터의 뼈대 — 마지막 4개 값의 합을 유지합니다. Day 4 링 버퍼의 예고편.

#include <stdio.h>

double moving_avg(double x) {
     double buf[4] = {0};      // 호출 사이에 유지되어야 한다
     int idx = 0;
     double sum = 0;
    sum -= buf[idx];               // 가장 오래된 값 빼고
    buf[idx] = x;                  // 새 값 넣고
    sum += x;
    idx = (idx + 1)  4;        // 0,1,2,3,0,1,...
    return sum / 4;
}

int main(void) {
    double in[] = {25, 25, 25, 25, 37, 25, 25, 25};
    for (int i = 0; i < 8; i++) printf("%.2f ", moving_avg(in[i]));
    printf("\n");    // → 6.25 12.50 18.75 25.00 28.00 28.00 28.00 28.00
    return 0;
}

오늘의 여섯 문장

  1. 컴파일은 전처리 → 컴파일 → 어셈블 → 링크. "undefined reference" 는 링크 에러다 (D1-1)
  2. 선언은 .h, 정의는 .c. 헤더 가드로 재정의를 막고, Makefile 의존성에 헤더를 적는다 (D1-2)
  3. 자료형은 바이트 수와 해석 규칙이다. 넘치면 잘리고, 같은 비트도 signed/unsigned 로 다르게 읽힌다 (D1-3·D1-4)
  4. int 와 unsigned 를 섞으면 int 가 unsigned 로 변환된다. -1 < 1u 는 거짓 (D1-5)
  5. = 과 ==, & 와 &&, 시프트 괄호, switch 의 break — 네 함정은 전부 -Wall -Wextra 가 잡는다 (D1-6)

  6. 인자는 값 복사, 지역 변수는 스택, static 은 데이터 영역. 재귀는 깊이를 알 때만 (D1-7)
